# 0.16.5 PiPで音声だけ流れて映像が待機する問題

利用者はPiPで映像が読み込み中になり、音声だけ続くことを報告。その後、アプリ再起動で解消した。再起動はWebKit／AVPlayer／映像表示の一時状態を作り直すため、切り替え途中の状態不整合が疑われる。保存されたWebキャッシュの容量不足が原因だと判断する証拠はなく、キャッシュ削除は行わない。実機の当該症状を再現したとは扱わない。

コード上、PiP開始時に全画面アダプターがfullscreenchangeを通知してDOM属性・Popoverを復元し、親iframeやアプリの表示サイズも変更する経路があった。サイト側のプレーヤー再構築やiOSへの映像レイヤー引き渡しと競合し得る。PiP中はこれらを保留し、元の要素・スタイル・表示領域・終了通知の状態を保つ。PiP終了後、実際の表示モードを確認して次の表示フレームで復元する。親iframeにも保持状態を伝える。Native全画面へ戻る場合はその状態を保ち、遅れて届く終了処理は世代番号で棄却する。復帰時に終了イベントが欠落していても、実際にinlineへ戻っていることを確認して保留状態を解消する。

ネイティブのライブキャンバスも、PiP中と非アクティブ中は元のWKWebViewのboundsを変更しない。実際の前面inline復帰後にメインキューの次の処理で通常の表示領域へ戻す。タブ一覧用の親コンテナの移動・選択枠は維持する。OS所有のPiP中は、追加のオーディオカテゴリ再設定を避ける。自動向き調整からPiPへ移る時も向きの制限を解除するだけにし、元の向きへの強制回転要求をその場で送らない。前版のWeb playback保持・ロック継続の方針は維持し、build14のupdateMedia/mediaScriptはバイト単位で同一。

復帰時は実際のPiPモードを確認して、全画面アダプターに残る保留状態を解消する。従来のメディア監視の内部フラグを直接上書きしたり、イベントを合成して状態通知を作り出したりしない。再生・停止・PiP終了・リロード・プレーヤー置換・キャッシュ／ユーザーデータ削除は行わない。

ローカル確認では、音声方針の保持に加え、実Chromiumの動画のrequestVideoFrameCallbackが進むこと、PiP状態の間にスタイル・Popover・fullscreenchange回数が変わらないこと、親iframeも表示領域を保持すること、終了後に復元すること、終了通知が欠落しても前面復帰時の実モード確認で保留状態を解消できることを確認する。PiP状態とiOSネイティブ呼出しは模擬であり、これを実機のPiP映像描画の成功とは扱わない。

直前の実機テストを利用者が行う希望を引き継ぎ、長いiOS UI検証は実行せず、Release実機用ビルド・IPA検査・配信・公開取得確認を行う。通常CIは変更しない。
