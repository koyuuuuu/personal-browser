# パスワード即時入力の仕様

調査日: 2026-11-10。対象: 現在のWKWebViewブラウザ、iPhone / iOS 18.4.1を含む既存対応範囲。

2026-11-10に本仕様の実装と、新サイトでの自動保存・更新提案の追加をユーザーが承認。実機検証済みとは扱わず、CI・配布結果を別途記録する。

## 採用する方式

ブラウザ内の既存の暗号化保管庫を使い、ログイン欄を選択するとキーボード直上に細い1行の候補バーを出す。候補を押すと、そのページにユーザー名・パスワードが入る。入力のために管理画面へ移動させない。

Apple標準のパスワード候補がiOSから提示される経路も維持する。Apple標準候補とブラウザ内の候補は別の保存先であり、ブラウザ内の候補にAppleの保存データを直接列挙・同期できるとは表示しない。

## 調査結果と選定理由

| 方法 | 確認できた範囲 | 今回の判断 |
| --- | --- | --- |
| AppleのQuickType候補 | 対応する入力欄の選択によりOSが提示し、候補選択と必要な端末認証を経て入力する。HTMLのautocomplete指定で認識を補助できる。提示内容や認証はOSが管理する | そのまま利用可能にする。独自ボタンから特定のApple保存パスワードを必ず即入力させる機能としては扱わない |
| ブラウザ保管庫からアプリ内の候補バーへ表示 | 自分の保管庫なので、解除後の一致アカウントを候補にし、選択したアカウントを現在のフォームへ入力できる。既存コードに保存・取り込み・解除・直接入力がある | 主経路として採用。既存保管庫を再利用する |
| ブラウザ保管庫をiOS全体のAutoFillプロバイダーにする | Credential Provider拡張とAutoFill Credential Provider entitlementをホスト・拡張へ追加する別方式 | 今回は採用しない。アプリ内入力には不要で、署名・データ共有・他アプリ対応まで範囲が広がる |

ネイティブアプリのAssociated Domainsによる資格情報共有と、Web上のHTML入力欄に対する標準AutoFillは区別する。「閲覧する全サイトとAssociated Domains契約がないと標準入力は一切使えない」とは結論づけない。一方、公開APIで任意のApple保存パスワード一覧を自前の候補UIへ読み出せる仕組みは今回確認できず、それを前提にした仕様にはしない。

ASCredentialDataManagerも確認したが、公式文書上iOS 26.2以降で、資格情報の保存・更新通知を渡すAPIである。現在の対象OSでAppleの保存一覧を読み出す解決策にはならない。

## 表示と配置

- 通常の文字サイズでは高さ44ptを基本にした1行。大きな文字設定では読みやすさとタップ領域を優先する。
- 例: `🔑 example.com  [user@example.comで入力] [別のアカウント]`。候補は横スクロールできる。ドメインやアカウントを見分けられる表示を残し、パスワード自体は表示しない。
- 表示条件は、選択中・前面のタブで、対応するユーザー名欄または現在のパスワード欄にフォーカスがあること。通常の検索・アドレス・新規パスワード・確認コード欄では出さない。
- キーボード表示時は、その直上のアプリ領域へ配置する。候補バーとキーボードの間に下部アドレスバー・ツールバーを挟まない。該当ログイン欄の編集中は下部chromeを一時的に退避し、入力終了後は従来の表示状態へ戻す。保存済みのツールバー設定は書き換えない。
- AppleのQuickTypeなど標準キーボードUIを置き換えない。標準候補が出た場合、自前のバーは標準キーボードUI全体の上に置く。
- ソフトウェアキーボードを閉じたら隠す。外部キーボード利用時は、対応するログイン欄のフォーカス中だけ画面下の操作可能な位置に出す。
- 管理・取り込み・編集はメニューの「パスワード」から開く。候補バーを管理画面への常設入口で占有しない。入力失敗時も管理画面へ自動遷移しない。
- 現在の「Appleのパスワード」は保存アカウント候補ではなく、フォームへフォーカスを移す入口である。新しい主候補バーから外し、標準AutoFillの説明・設定側へ整理する。

## 押したときの動作

| 状態 | 操作と結果 |
| --- | --- |
| 解除中・一致するアカウント1件 | アカウント候補を1回押すと入力。管理画面も追加の確認画面も開かない |
| 解除中・複数件 | アカウント候補を横に並べ、選択したものを入力。多い場合の「別のアカウント」は該当サイトだけの小さな選択UIを開き、選択すると入力。全保管庫の管理画面は開かない |
| ロック中 | 汎用の「保存済みパスワードを入力」を表示。押すとFace ID等の既存の端末認証を実行。一致1件なら認証成功後、その操作の続きとして入力。複数件なら同じバーに候補を出して選ぶ |
| 解除後に一致0件 | 「このサイトの保存情報なし」と、明示的な登録・取り込み操作への入口を表示。無関係なサイトの資格情報を代用しない |
| 認証取消・失敗・対象フォームの変化 | 入力を中止。自動で認証を繰り返したり、別フォームを代わりに選んだりしない |

ロック中は一致件数もアカウント名も分からない既存設計を維持し、汎用ボタンがあることを「このサイトの保存パスワードあり」とは表示しない。

「すぐ入力」は解除中なら1タップ、ロック中ならボタン→必要な端末認証→入力という意味。認証不要を保証しない。自動ロックは既存設定の30/60/300秒を維持し、初期値60秒を無断で延長しない。バックグラウンドと明示ロックで即時ロックする。

入力後はページ上で内容を確認できる状態を保ち、ログインボタンの押下・フォーム送信は行わない。ユーザー名だけの段階ではユーザー名だけを渡す。明示的な候補選択は選んだアカウントへの差し替え操作とし、既存の任意の無操作自動入力は別設定として維持する。今回の操作を実現するために無操作自動入力を有効化する必要はない。

## 保存データ

既存の暗号化保管庫、鍵、保存形式、バックアップを再利用する。初回だけ既存の登録またはSafari/Braveから書き出したファイルの取り込みを行えば、その後の通常入力は候補バーで完結する。書き出し手順は元アプリ・OS・端末に依存する。Appleの保存先と自動同期したり、他アプリの非公開データを読んだりする機能ではない。

候補表示のためにフォームのパスワード値を常時取得しない。新規保存・更新は利用者のフォーム送信時に自動検出し、ネイティブの提案から確認して確定する。文字入力中は取得せず、利用者の実際の送信操作直前の候補をメモリに最長120秒だけ置く。ログイン成功そのものを断定しない。確認ボタンで暗号化して保存し、同じアカウントはID・メモ等を保ってパスワードだけ更新する。同じ保存内容なら提案しない。新しいパスワードと確認欄が異なる場合は提案しない。プライベート、別オリジン送信、プログラムだけの送信は対象外。バックグラウンド・明示ロック・タブ変更・別サイトへの移動・期限切れで未確定の候補を破棄する。送信検出は標準フォームとsubmitボタンを使うAJAXを対象とし、独自ボタン・閉じたShadow DOM等すべてのサイトの自動検出は保証しない。チャット・GitHubへ実際のパスワードファイルを送る必要はない。

## 実装方針

1. `PasswordSuggestionBar`を、サイト検出時に常設する複数行のUIから、フォーカスに追従する入力用1行UIへ変更する。
2. キーボード内のQuickTypeへの独自候補挿入は前提にせず、公開APIのUIKeyboardLayoutGuideでキーボードの表示状態を観測し、アプリ内の末尾に候補バーを置く。キーボード回避はSwiftUIだけが担当し、観測した高さを別に足し引きしない。iOS 15以降にあるAPIなので現在の対応範囲で採用可能。WebKitの内部コンテンツビューのクラス変更、メソッド差し替え、非公開のキーボード呼び出しには依存しない。
3. root側で候補バー・キーボード・chrome・Web表示の高さを一度だけ分配する。SwiftUIの自動キーボード回避とUIKitの計測を二重適用しない。非表示時の予約高は0。候補バーの出入りでWKWebViewを作り直さない。
4. `PasswordFormController`と`PasswordFormScript`のフォーカス通知を改善する。focusinだけでなくfocusout・対象消滅・別入力欄への移動を扱う。フォーム値は通知へ追加しない。
5. 現在の「フォーカスがなければ最初のフォームを選ぶ」処理を候補入力には使わない。操作開始時に実際の対象フォームを固定し、ボタンを押したこと自体による一時的なフォーカス移動では対象を失わないようにする。
6. 認証待ちも1つの入力操作として扱う。タブ変更・ページ遷移・バックグラウンドで取り消し、認証後はタブ、文書nonce、フォームID、frameと送信先、HTTPSの信頼性、資格情報の有効性を再検証する。古い対象から別フォームへ黙って切り替えない。
7. Face IDによる一時的なinactiveでは、機密表示を隠しつつWeb表示・フォーカス・レイアウトの連続性を保つ。バックグラウンドへの移行とは区別する。
8. 既存のscheme/host/port完全一致、証明書・同一オリジン検証、プライベート入力の初期オフを維持する。HTTP、異なるサイトのiframe、対象不明・曖昧なフォームへは入力しない。

## 実装時の確認項目

- Core: ロック/解除、0/1/複数候補、対象固定、認証中のタブ変更・遷移・背景化、ユーザー名だけの入力を確認する。
- 関連する既存の保管庫UIケースを拡張し、管理画面を開かずにロック→認証→1件入力、複数候補選択、非送信を確認する。
- Release構成でも、キーボード表示前後、閉じる操作、縦横回転、上/下ツールバー設定で候補の位置と実際のタップを確認する。非ログインページではバーの予約高0とWeb表示の非消失を確認する。
- 実機: iPhoneのFace ID後の入力継続、ソフトウェアキーボード・標準AutoFillとの共存を確認する。CIの偽認証をFace ID確認済みとは扱わない。
- Appleの実際の保存候補はアプリ側から読まず、利用者の端末で表示と選択を確認する。全サイトでの標準候補表示を保証しない。
- 保存形式を変更しない範囲では旧データ往復・全UI・無関係な音声テストは増やさない。保存ロジックまで変更する場合は、その差分に応じて検証計画を見直す。
